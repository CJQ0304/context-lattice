# 真实场景测试报告（v1.2.x 轮）

> 本报告记录**开发期**的测试方法与数据，供追溯与复核。`tests/` 与 `docs/` 只在 GitHub 仓库里存在，
> **不随技能安装包分发**（平台只接受 references / scripts / templates 等运行件）。
>
> ⚠️ **所有绝对值都绑定交付包版本**：语料 = 当前交付包的全部文本，改一次文档/脚本，T 就变。
> 引用时请连版本号一起引。百分比（净省）是相对稳定的那个量。

## 0. 为什么要另做一轮"真实测试"

前几轮的证据有两处弱点，这轮专门补上：

| 弱点 | 这轮的补法 |
|---|---|
| 语料是**合成的规模库**（T40/P120/R360），不是真实素材 | 层 A 改用**真实交付包**的 14 个文件做语料 |
| 行为层只有**机械断言**，没有真实执行者 | 层 B 派**两个独立实例**跑同一道真实需求 |

两层都刻意避免"作者挑有利场景"：层 A 的基线是机械量（语料全文 token），层 B 的判据在**看到产物之前冻结**。

---

## 1. 层 A：真实语料上的读取账（机械测量，可复现）

复现：`python tests/benchmarks/realworld-probe.py`（需要 `tiktoken`）

语料 = 交付包 14 个文件 = **86,276 token**（真实文件，非合成）。

> **分母是随版本走的**：这个数等于「当前交付包的全部文本量」。此后每改一次文档，
> 绝对值都会变（T、W、净省会一起动），所以引用时请连着版本号一起引。
> 脚本已经不再手抄文件名清单，改为从交付包边界（`tests/pkg_boundary.py`）现取 ——
> 否则手抄的那份会和实际包漂移，而分母一漂，整套数字就悄悄失效了。

**库的形态**（真实语料建库后的实际落盘）：`T9 P9 R17 E14`（共 49 个节点），库文件 3,314 字节、51 行、2,636 字符。

> **14 个事件节点指向 245,156 字节原文，库内只占 1,749 字符** —— 库内每 1 字符指向 140.2 字节原文。

**三个真实任务的读取账**（索引层 925 token / 2,145 字符）：

| 任务 | 工作集（保守） | 工作集（乐观） | 全量 | 净省（保守） | 净省（乐观） |
|---|---:|---:|---:|---:|---:|
| T1 给 `ctx.py` 加一个子命令 | 35,536 | 14,994 | 86,276 | **57.7%** | **81.5%** |
| T2 改 `SKILL.md` 的 description | 7,581 | 1,584 | 86,276 | **90.1%** | **97.1%** |
| T3 新增一条拆分规则 | 3,992 | 1,204 | 86,276 | **94.3%** | **97.5%** |

- **保守口径** = 任务涉及的文件整份读；**乐观口径** = 按结构边界（markdown 标题 / python `def`）切片后只读命中段。切片规则写在脚本的 `pick()` 里，可复核。
- 切片的命中率：`ctx.py` 7/68 段、`store-format.md` 7/13 段、`SKILL.md` 2/13 段、`split-rules.md` 4/16 段。

**门控判定**（真实 CLI `plan`，脚本算、不让模型估）：

| 场景 | 工作集 | 判定 | 净省 |
|---|---:|---|---:|
| 局部任务（T1 工作集） | 41.2% | **STORE** | **+52.1%** |
| 反例：任务要读完全部素材 | 100.0% | **INLINE** | **−6.7%** |

> `plan` **没有** `--reuse` 参数 —— 这正是本轮设计的结果：新口径下不需要预估复用次数 `k`，规则退化为「读过的块就压存」，一个需要预测的参数被消掉了。

**体积无关性验证**：把源文件正文翻倍（92,484 → 184,969 字节，+100%），视图 token 只从 82 变 84。

> 那 **+2** 不是泄漏：其中 1 个 token 可由 `bytes:` 字段位数从 5 位变 6 位解释，另一个在 token 切分边界上。**这是为可校验性付的必要代价，且是对数级的** —— 若正文真的进了视图，差值会是数万 token。

**事件节点全链路**（真跑）：索引里 14 条事件节点行、**索引中不出现正文**、`fetch --out` 取回的 sha256 与原件**逐字节一致**。

### 一处必须说明的口径差

`index` 报的索引层是 **925 token**，而 `plan` 报的导航层是 **5,757 token** —— 两者不是同一个东西：

- 925 = 我建的**库**的索引层（49 个节点，粗粒度：按文件 + 按约定）
- 5,757 = `plan` **对语料目录现算**的细粒度导航层（按每个结构单元）

**导航层做多细是取舍，不是定值**：粗粒度更省但定位精度低。这里把两个数都摆出来，不取一个好看的。

> 这两个数都由脚本从**实际输出**取（`plan` 的 I 是解析它自己的打印行），不再手抄 —— 旧版这里写死过一个常数，而同一次运行里 `plan` 打印的是另一个值，机器可读摘要与人读输出自相矛盾。

## 2. 层 B：两个独立实例跑同一道真实需求

**需求**（真实开发任务，不是问答）：

> 给这个存储格式新增一种行类型 `F <内容>`（缩进 4 格、与 `R` 同级，语义「外部依赖」，带 `w:<权重>` 字段）。回答：① 必须改哪些文件、哪些具体位置；② 必须新增/更新哪些不变量；③ 现有代码遇到不认识的行会**静默丢数据**还是**显式报错**；④ 实际读取过的文件清单。

**两臂的唯一差别**：A 臂的提示里告知"仓库里有一个技能包，可按其文档使用"；B 臂不提技能的存在（只说"仓库里有一个自定义文本格式"）。

沙箱在**工作区之外**（`%TEMP%/rw-sandbox`，15 个文件 / 68,312 token），两臂都看不到本项目的任何结论。

**判据**（8 条，在看到产物**之前**冻结，机械抽取证据）：`tests/benchmarks/rw-behavior-rubric.py`

| 判据 | 臂 A（有技能提示） | 臂 B（无） |
|---|---|---|
| P1 行分派（`parse`） | PASS | PASS |
| P2 渲染（`render`） | PASS | PASS |
| P3 计数 | PASS | PASS |
| P4 内容指纹（`_body_key`） | PASS | PASS |
| P5 增量归并（`apply_delta`） | PASS | PASS |
| P6 格式文档 + 不变量表 | PASS | PASS |
| P7 第 3 问主结论（显式报错） | PASS | PASS |
| P8 是否区分「入口报错」与「其他静默路径」 | PASS | PASS |
| **得分** | **8 / 8** | **8 / 8** |

**成本**（按两臂自报的清单机械核算，`:  python tests/benchmarks/rw-cost.py`）：

| | 读入 token | 占全量 |
|---|---:|---:|
| 臂 A（告知有技能） | 66,781 | 80.6% |
| 臂 B（不告知技能） | 86,276 | 100.0% |
| 差 | −19,478 | **−22.6%** |

> 两臂的清单是**自报**的，脚本只做机械核算（精读按全文计、部分读按区间计、纯检索不计）。
> 同样地，绝对值随交付包版本变动；百分比是相对稳定的那个量。

### 这个 −22.6% **不能算作技能的功劳**

A 臂省下的那部分，是它**少细读了两份 references**（`coverage-matrix.md`、`degradation.md` 只做了检索），属于**行为差异**，不是技能替它省了读取 —— 两臂都没有真的走"索引 → 局部读"的流程，都是直接用通用文件读取把工作做完了。

**结论：在这道题上，技能没有带来可归因于技能的收益。** 与之前 A/B 的"信息保真增益 0%"结论一致，而且这次是**两个独立实例**给出的。

### 这道题本身就落在技能的不利区间

"给格式加一种行类型"必须同时看懂**格式规范 + 全部实现分派点**，工作集天然接近全量。门控的判定印证了这一点：把 A 臂实际读的文件当工作集，**占全量的 75.1%**，净省仅 **+18.2%**。

> 注意门控这里仍判 **STORE**（75.1% ≤ 断点 93.3%）—— 也就是说它**没有**触发「不该建库」的硬红线，
> 但净省只剩十几个百分点，已经贴着边界。这正是前几轮反复得出的那条边界的真实形态：
> **决定收益的是任务的局部性，不是技能**。任务是"把整个格式实现通读一遍"时，任何读取源替换都救不了。

## 3. 真实测试挖出了什么（这才是它的主要价值）

### 3.1 一处**真缺陷**（第 23 处）：交付包内有悬空引用

臂 A 在做真实需求时，顺着 `ctx.py` 的注释去找一份**并不存在的参考文档**（注释里写了一个 `references/` 下的事件节点专文），**发现这个文件根本没有** —— 事件节点的规则实际并在 `store-format.md` 里。

- 性质：人读文档时看不出来（引用读起来完全合理），只有机械扫才拦得住；代价很实（下载者按图索骥会扑空）
- 修复：改注释指向 `store-format.md` 的「事件节点」一节
- 防线：**新增套件 14 · 交付包自洽（无悬空引用）**，并配负向注入（插入一条假引用，确认会红）
- 检查器**已知局限**：只识别 ASCII 文件名的引用形态。这个局限是实测出来的 —— 第一次负向注入用中文名做探针，检查器完全不响。

### 3.2 一处**结构性脆弱点**：`kind` 是隐式的（缺省即 R）

两臂**各自独立**指出同一件事：代码里所有 `if kind == "E": ... else: 当 R` 的兜底，在新增第三种行类型时会把新类型**静默降级**（渲染成 R、计入 R 计数、折叠时被删掉，且一个错误都不报）。

- 定性：**不是现在可触发的 bug**（`parse` 只产出 R/E），是**未来扩展的陷阱**
- 而且两臂各自列出的位置有重叠但不完全相同 —— 说明这类脆弱点是**弥散**的，靠人肉排查不可靠
- 修复：新增 `LEAF_KINDS` 白名单 + `_kind()` 访问器，把「缺省 = R」改成「未知 = 报错」，改掉 6 类分派点
- 防线：4 条新断言 + 负向注入（把 9 处调用点退回旧写法 → 4/4 命中）

### 3.3 两处**裁判自身误判**（累计第 4、5 处）

| # | 误判 | 修法 |
|---|---|---|
| 4 | P8 原写成"出现『静默』即判为编造"，把两臂**额外发现的**其他静默路径误判成编造 —— 而那恰是答案里最有价值的部分 | 改为正面判据：既要给主结论（显式报错），又要指出至少一处其他静默风险 |
| 5 | 告警规则没排除否定语境，把「**不会**静默丢数据」误报成"主结论写成静默" | 补否定 lookbehind，并配正负控（坏样例 True / 好样例 False） |

两处修正**都朝不利于"技术手段有效"的方向**（先压低了两臂得分，再纠正回来）。

## 4. 这轮结论

1. **层 A 的确定数据**：真实语料上，局部性好的任务净省 **58%–94%**（保守口径，真去读要改的那些文件）/ **82%–98%**（乐观口径，按结构切片只读命中段）；工作集接近全量时净省 **−6.7%**（反而更贵）。门控在真实语料上判定正确（STORE / INLINE 各一例）。
2. **层 B 的不利数据**：给格式加特性这类任务，两个独立实例**同分 8/8**，A 臂成本低 19.4% 但**不可归因于技能**。
3. **真实测试的主要收益不是"证明技能有用"，而是挖出了 1 处真缺陷 + 1 处结构性脆弱点**，并各自补上了可复现的防线。
4. **边界（必须一起读）**：
   - 层 B 的 `n=2`、执行者与作者同源、单题单轮。
   - 层 A 的工作集口径有两个（保守/乐观），真实值落在区间内，不是一个点。
   - 索引层的尺寸取决于"索引做多细"这个取舍，粗粒度与细粒度差 6.2 倍。
