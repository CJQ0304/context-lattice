# 宿主记忆适配层：把三层作用域接到实际的三层记忆上

> **本文件是「适配层」，不是内核。** `scripts/ctx.py` 完全不依赖本文件描述的目录结构——它只认 `.ctx` 文件路径。
> 也就是说：**换一个宿主环境，内核照常可用，只是这张映射表要重画。**

## 一、为什么要单独一层

内核要做「通用为体」，就不能把「工作区备忘录放在哪」这种环境事实写进代码。但用户真正的问题恰恰是**「我的记忆散在好几个地方，回顾时不知道上哪找」**——这是环境问题，只能用环境方案回答。

于是分成两层：

| 层 | 内容 | 是否随环境变 |
|---|---|---|
| 内核 | `.ctx` 格式、作用域枚举、生命周期标记、`index`/`find` | ❌ 不变（可移植） |
| 适配层 | 「哪个目录对应哪个作用域」「30 天蒸馏怎么接」 | ✅ 随环境变 |

## 二、映射表（以 WorkBuddy 环境为例）

工作区记忆系统本身就有三层，且**恰好与本技能的三层作用域一一对应**：

| 本技能作用域 | 宿主记忆层 | 实际路径（示例） | 生命周期策略 |
|---|---|---|---|
| `user` | 用户级本地记忆 | `~/.workbuddy/user-<id>-personal/MEMORY.md` | 长期；用户显式要求才改 |
| `proj` | 工作区长期备注 | `<workspace>/.workbuddy/memory/MEMORY.md` | 长期；按主题蒸馏 |
| `task` | 工作区每日日志 | `<workspace>/.workbuddy/memory/YYYY-MM-DD.md` | **追加即弃**；30 天后蒸馏进 `proj` |

对应到 `.ctx` 分区（当需要结构化存储时）：

```
<记忆根目录>/
├── index.txt              # ctx.py index 产物（可选，纯导航）
├── user/
│   └── prefs.ctx          # scope:user
├── proj/
│   ├── skill-dev.ctx      # scope:proj:skill-dev
│   └── layout.ctx         # scope:proj
└── task/
    └── 2026-10-15.ctx     # scope:task:2026-10-15
```

**为什么映射关系这么顺**：两边都是「持久度递减」的三档，用的还是同一套判定问句（换个工作区还成立吗 → 跨会话还要用吗 → 只是这次吗）。所以不是「硬凑」，是同一个分类在两种载体上的两种表示。

## 三、接线方式（两条路，按需选）

### 路线 A：纯文档记忆（不引入 `.ctx`）

宿主本来就有 `MEMORY.md` 与日志，此时**只需借用判定程序**，不必生成 `.ctx` 文件：

- 往 `user MEMORY.md` 写之前，先过一遍 `lifecycle.md` 第 0 步判定；
- 判定为 `task` 的内容写进当日日志，不污染长期备注；
- 日志超过 30 天时，用「标记 × 年龄」口径蒸馏：`暂态` 类直接淘汰、`长期` 类升格进工作区 `MEMORY.md`。

**这条路的价值**：即使一个 `.ctx` 文件都不建，光靠「写之前先问一句这条该在多大范围生效」就能显著减少记忆污染。**本技能的判定程序是可以脱离存储格式单独使用的。**

### 路线 B：结构化记忆（引入 `.ctx`）

内容量大、需要渐进下钻时，用结构化存储：

1. 按上表建 `user/` `proj/` `task/` 三个分区目录；
2. 每份 `.ctx` 在 `init --scope` 时声明作用域；
3. 定期 `index --root` 生成跨库索引；
4. 回顾时 `find --root --topic …` 定位 → `read --topic …` 取子树；
5. 老化时 `prune --aging --days N --today …`，升格候选 `--emit-promote` 到更持久的分区。

**路线 A 与 B 可以共存**：`.ctx` 存结构化内容，`MEMORY.md` 存需要人直接读的散文式约定。两者不冲突，因为 `MEMORY.md` 是给人读的，`.ctx` 是给模型读的。

## 四、30 天蒸馏怎么接（补上宿主流程缺的那一环）

宿主记忆规则里写了「30 天以上的日志蒸馏进 `MEMORY.md`，然后删掉旧文件」，但**从未说明凭什么判断哪条值得留**。这一环现在有了判据：

| 日志里的内容 | 判据 | 动作 |
|---|---|---|
| 用户明确要求记住的 | `钉住` | 升格进 `proj`（或 `user`，若跨项目成立） |
| 反复出现的约定 | 第二次出现 | 升格进 `proj` MEMORY.md |
| 已完成的临时结论 | `暂态` 且已结 | 淘汰，不蒸馏 |
| 未表态但不碍事的 | 无标记 | **保留**（默认不丢） |

蒸馏的动作细节：

- **先判作用域，再判去留**：一条日志内容如果换个工作区也成立，应该进 `user` 而不是 `proj`，否则换项目时会丢。
- **蒸馏是「升格 + 淘汰」，不是「搬家」**：只有经得起「换个工作区还成立吗」的内容才配进更持久的层；其余的自然淘汰。
- **保留蒸馏痕迹**：源日志的删除是**不可逆操作**，执行前必须让用户确认，并说明将要删除哪些文件。

## 五、边界与风险

1. **不要用本技能覆盖宿主记忆机制**。宿主的三层记忆有自己的写入时机与格式（`MEMORY.md` 是给人读的散文），`.ctx` 是给模型读的结构。两者定位不同，**互操作 ≠ 互相替代**。
2. **目录约定是运行假设**：本文件描述的 `user/ proj/ task/` 路径是**建议**，不是内核要求。宿主换了目录结构，改这张表即可，不用改内核。
3. **`mismatch` 要当信号看**：库目录与 `scope:` 声明不一致时内核只提示不报错，但这通常意味着「文件被放错地方了」——**放错地方的记忆比没有记忆更危险**，因为它会在错误的范围里生效。看到 `mismatch` 要处理，不要习惯性忽略。
4. **跨环境的可移植性边界**：内核可移植，**判定程序也可移植**（它只是几条问句），但**目录映射与 30 天蒸馏的具体接法不可移植**——这是本文件存在的全部理由。
