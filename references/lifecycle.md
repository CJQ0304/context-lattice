# 作用域与生命周期：让记忆「知道自己在多大范围里生效」

> 本文件回答两个 `split-rules.md` 不回答的问题：**这条内容该在多大的范围里生效**（作用域），以及**它该活多久**（生命周期）。
> 格式细节见 `store-format.md` 第五之二 / 五之三节；与宿主三层记忆的接线见 `host-memory-adapter.md`。

## 一、为什么需要这一层

同一句「以后回复都用中文」，和「这次先按 A 方案试一版」，在结构上是同一种东西（都是一个 `R` 行），但**寿命差了几个数量级**。不区分会出两类错：

| 错法 | 后果 |
|---|---|
| 把长期偏好在任务结束时丢掉 | 用户每换一个会话就要重说一遍 |
| 把某次任务的临时结论当成长期规范 | **记忆污染**：错误结论在错误的范围里反复生效，比记漏更糟 |

所以压缩存储要真正「可续」，必须给每条内容配一个**作用半径**和一个**寿命**。

## 二、三层作用域

| 作用域 | 作用半径 | 判定问句 | 典型内容 |
|---|---|---|---|
| `user` | 跨项目、跨会话 | 「换个工作区还成立吗？」换成别的项目也依然成立 | 称呼与语气偏好、语言选择、通用工作习惯 |
| `proj` | 当前工作区、跨会话 | 「只在这个工作区成立，但下次开新会话还要用」 | 目录约定、构建命令、架构决策、交付形态 |
| `task` | 本次会话 / 本次任务 | 「这件事做完就不需要了」 | 临时方案、本轮待办、试验性结论 |

**限定名**用于同名多实例：`proj:demo`、`task:2026-10-15-brand`。限定名只允许字母数字与 `_ . -`。

### 判定程序（第 0 步，先于 `split-rules.md` 的四步）

```
这条内容要不要入库？           → 否，按 split-rules.md 的「不入库」清单处理
  ↓ 要
它归到哪个作用域？              ← 本文件
  ① 换个工作区还成立？          → 是 → user
  ② 只在本工作区成立，但跨会话？ → 是 → proj
  ③ 只是这次的事？              → 是 → task
  ④ 说不清？                    → task（宁可窄不可宽，见风险）
  ↓
它归到哪个事物（T）？           ← 回到 split-rules.md 第 1 步
  ↓
它归到哪个目的（P）？           ← split-rules.md 第 2 步
  ↓
它是要做什么，还是要做成什么样？ ← split-rules.md 第 3–4 步
  ↓
它的寿命？                      ← 本文件第三节
```

**第 ④ 条是这套判定的安全阀**：域判错的成本是不对称的——**污染 > 漏记**。漏记只是要多问一次；污染会让一条错误结论在错误范围里持续生效，而且很难被发现（因为它看起来「有出处」）。所以拿不准一律写 `task`，等它第二次出现再升格。

### ④ 的高频实例：对技能自身的元讨论

「你这个格式我看不懂，改改」「帮我把这个工具的默认行为调一下」这类**关于工具自身**的输入（归入专用事物 `元·工作方式`），
作用域**默认取 `task`**。判定理由：这类话是对**当前这个实例**的诉求，而不是一条跨项目的通用规范；
判成 `user` 会让一次性的抱怨在别的项目里也开始生效——这正是「污染」的典型形态。

只有用户**明说**「以后所有项目/所有技能都照这个来」时，才按 ① 升成 `user`。

> 这一条是**行为层探针补上的**：在补它之前，两次独立执行都把「你这个 skill 的格式改改」判成了 `user`（污染方向错误 2/2），
> 说明规则原文的沉默会稳定地导向宽判。（行为层验证的完整方法学与逐条结果保留在开发仓库的质检记录里，**不随本包分发**。）

## 三、生命周期标记与老化

标记复用行尾 ` [xxx]` 语法，三个词被 `prune --aging` 特判：

| 标记 | 动作 | 语义 |
|---|---|---|
| `钉住` | 永不自动老化 | 用户明确要求长期记住，优先级最高，任何自动流程都不动它 |
| `长期` | 超期不删，列为**升格候选** | 超出当前作用域寿命，看起来值得在更持久的作用域里生效 |
| `暂态` | 超过 `--days` 即**折叠**（删除） | 用完即弃 |
| 无标记 | **不动**（默认保留） | 未表态的内容不承担被自动删除的风险 |

### `prune --aging` 的口径

```
ctx.py prune -f <库> --aging --days N --today YYYY-MM-DD [--emit-promote FILE] [--force]
```

- **年龄 = 头部日期 与 `--today` 之差**，必须显式给 `--today`：日期不能由脚本猜，否则同一条命令不同天跑出不同结果（违反可复现原则）。
- `--days` 必须显式给，且不可为负。
- `--today` 早于头部日期 → 报错（时间倒流），不静默取绝对值。
- **只有 `暂态` 会被删除**；`长期` 只被列出并输出成升格增量；`钉住` 与无标记内容一律保留。
- **事件节点（`E` 行）完全不受老化影响**：它既不被折叠、也不进升格候选，无论有没有标记。理由是**原文不可再生** —— 库里那行只是指针，折叠掉它等于把回原文的路堵死。要处置它只有一条路径：把它显式标成 `[已废]`，再走 `prune --drop-stale`。`--collapse-done` 同样不动 `E`，并在有保留时报一行 `NOTE 折叠保留了 N 个事件节点`。
- 输出**必须打印实际计数**（折叠几条 / 钉住跳过几条 / 无标记保留几条 / 升格候选几条），且收尾的 `-xR` 必须与真实删除数一致。

### 升格增量（`--emit-promote`）

被列为升格候选的 `长期` 条目会输出成一个**标准增量文件**，可以直接喂给目标库：

```
// 由 ctx.py prune --aging --emit-promote 生成的升格增量
// 里面是标记为 [长期] 且已超过老化阈值的条目 —— 它们看起来值得在更持久的作用域里生效。
// 用法：ctx.py add --file <目标库路径> --stdin < 本文件
// 注意：本文件只搬运内容，源库副本不会被自动删除；请在目标库确认无误后再自行处理源库那份。
T 临时任务
P 试一版
R 这条要长期留着 [长期]
```

两条硬约束：

1. **只搬运，不删除源**。升格是「复制到更持久的作用域」，不是「移动」。源库那份是否清理，由调用方在确认目标库无误后自行决定——自动化删除会丢审计轨迹。
2. **升格需要显式确认**。`--aging` 只是**列出候选并生成文件**，不会自动写入任何目标库。是否有资格升格最终由人（或明确授权）决定。

## 四、升格判据：只用写入侧可见的显式信号

「什么内容值得升格」不能靠猜。本技能**只承认三种显式信号**，全部来自写入侧：

| 信号 | 形态 | 说明 |
|---|---|---|
| 用户明说 | 「以后都这样」「记住这个」 | 最强信号，可直接升格 |
| 同类内容第二次出现 | 同一 T/P 在不同任务库里再次落库 | 说明不是一次性的 |
| 显式重复声明 | 增量里带了 `长期` 标记 | 写入者主动表态 |

**刻意不做的**：不通过 `read` 的访问次数来自动升格。原因是 `read` 必须保持**严格只读**（无副作用），这是已验证的不变量；让 `read` 记录访问会打破它，并让「只读」这个语义变得不可信。代价是升格偏保守、可能漏升——这是**有意识地选择保守**：漏升只是少升一条，误升会污染长期记忆。

## 五、跨库导航：先进索引，再取子树

三个作用域的库可能分散在不同目录。回顾时应**先读索引、再定位，最后才取子树**：

```
ctx.py index --root <记忆根目录> --date YYYY-MM-DD [--out FILE] [--kind user|proj|task]
ctx.py find  --root <记忆根目录> --topic <名> [--purpose <名>] [--kind …] [--exact]
```

这把 `--level 1 → 2 → 3` 的**渐进下钻从「单库内部」提升到「全库之间」**：

1. `index` 只吐键层（作用域 + 事物名 + 目的名），体积与实际内容量无关；
2. 用 `find` 定位到具体库与子树；
3. 只对命中的那个库做 `read --topic …` 取回完整内容。

三条纪律：

- **索引是导航，不是真相**：内容以各 `.ctx` 为准；不一致时报错重建，不猜。
- **索引缺失或过期时逐库扫描必须仍然可用**——索引只能是增强，不能是主干硬依赖。
- `find` 命中 0 时**必须明说 0 命中**，不得把「没找到」表述成「不存在」。

## 六、失效信号（什么时候这套判定不适用）

| 信号 | 含义 | 处置 |
|---|---|---|
| 用户反复改口作用域 | 说明判定问句问错了（多半是「换个工作区还成立吗」被理解偏了） | 停下来把三档用**具体例子**复述一遍，请用户选 |
| 几乎所有内容都判成 `task` | 判据被用成了「没把握就 task」的兜底，失去区分力 | 回看是否有 `proj` 级约定被漏判；但要确认确实没有，别为了「看起来有用」硬升 |
| 库目录与 `scope:` 频繁 `mismatch` | 目录约定与声明脱节 | 要么修目录、要么修声明；不要无视 mismatch 继续跑 |
| 升格候选越堆越多却从不确认 | 升格文件形同虚设 | 明确告知用户「有 N 条候选待确认」，把决定权交回去 |

> **反膨胀提示**：给每条内容都打生命周期标记会让存储明显变长。标记只在**有实际寿命判断**时才打；无标记是合法且默认的状态，不代表「忘了打」。
