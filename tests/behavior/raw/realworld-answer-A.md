# 新增行类型 `F <内容> | w:<权重>`（外部依赖，缩进 4 格，与 R 同级）——改造清单

> 结论先行：`F` 不是「多认一个字符」这么简单。它同时落在 **解析、渲染、计数、指纹、预算、导出、索引、老化、模板、不变量文档** 九个环节上；
> 漏掉其中任何一个，「非 E 即 R」的默认分支就会把 F 悄悄降级成 R（Q3 的静默路径）。
> 本文中的行号基于当前 `context-lattice/scripts/ctx.py`（1985 行）。

## 问题 3：现有代码遇到 F 行——静默丢数据还是显式报错？

### 结论：**入口层是显式报错（EXIT 1），但有三处是静默的**，且其中一处在多库场景下会让**整个库凭空消失**。

已实测（Python 实跑，非推断）：

**① 单库入口 — 显式报错 ✅**

| 函数 | 位置 | 行为（实测） |
|---|---|---|
| `parse()` | L326–L356 | 手改文件里出现 `    F 依赖外部 API \| w:3` → `ERROR 第 5 行：缩进 4 格的行必须是 ``    R 内容``（要求）或 ``    E ...``（事件节点）`，**exit 1**。F 行未被静默吞掉，而是整库拒绝解析 |
| `apply_delta()` | L555–L565 | `add --stdin` 喂 `F 依赖外部 API \| w:3` → `ERROR 增量行无法识别：``F 依赖外部 API \| w:3``；行首标记只能是 T（事物）/ P（目的）/ R（要求）/ E（事件节点）`，**exit 1** |

也就是说：**没有「解析成功但 F 被丢掉」的单库路径**——因为 `parse()` 是唯一入口，未知 4 格行一律在这里被拦下。

**② 多库聚合入口 — 静默丢整个库 ⚠️（这是真正危险的一处）**

`cmd_index()`（L1713–L1780）与 `cmd_find()`（L1783–L1840）都走 `_scan_stores()`（L1681–L1703）：L1691–L1693 把 `CtxError` 收进 `skipped`，**该库直接不进索引体**，然后由 `_report_skipped()`（L1706–L1710）只往 **stderr** 写一行 `NOTE`，`cmd_index`/`cmd_find` 仍返回 `EXIT_OK`。

实测：一个含 F 行的库 + 一个正常库同处一个 root 时——

```
#IDX 1 | 2026-10-16 | stores 1 | T1 P1        ← 含 F 的库不见了
HIT - | proj/good.ctx | T1 品牌定位 | P1.1 确定目标人群
OK find 1 命中（扫描 2 个库，跳过 1 个；条件 topic=品牌定位）   ← exit 0
```

后果：若某个库被**新版本**写入过 F 行，而系统里跑的是**旧版本**内核，那么 `index`/`find` 会**整体漏掉这个库**——导航层上看它是「不存在」，而 `find` 仍宣称「扫了 2 个、跳过 1 个、命中 1」，退出码 0。**这是 F 作为破坏性行类型真正会咬人的地方**（也正是 `store-format.md` §八 第 13 条所依赖的「索引缺失时逐库扫描仍可用」在这条路上并不成立：扫描确实跑了，但结果是坏的，且没有提升退出码）。

**③ 代码内部的「非 E 即 R」默认分支 — 潜在静默降级 ⚠️**

下列位置都只有「是 E / 不是 E」两路，凡不是 E 的条目一律按 R 处理。F 一旦进入数据模型而漏改其中任何一处，就会**无报错地把 F 当 R**（不是丢数据，而是数据降级/错算）：

| 函数 | 位置 | 静默行为 |
|---|---|---|
| `_fmt_item()` | L406–L411（L411 的 else） | 任何 `kind != "E"` 渲染成 `R <text>` → 落盘即把 F 改写成 R |
| `_counts4()` | L427–L429（`kind != "E"` 计入 R） | F 被计入 R 计数 → 头部 `R` 虚高、F 恒为 0 |
| `_count_lines()` | L892–L893 | 不数 F 行 → 视图头部自洽性被破坏（回灌失败） |
| `_body_key()` | L458–L459（else） | F 的指纹按 `R|...` 生成，**改权重被判 no-op → 不写盘、不递增 rev**（静默丢弃这次修改） |

**给 Q3 的一句总结**：单库读写是**显式报错**（`parse()` L355、`apply_delta()` L564），不会静默丢；但 (a) `index`/`find` 会把整库**静默漏掉**（只报 stderr NOTE，退出码 0），(b) 上述 8 处「非 E 即 R」的默认分支会在改造不彻底时把 F **静默降级成 R**。因此 F 上线前必须给这些默认分支加「未知 kind 即报错」的兜底，否则本次改造的核心风险不是「读不了 F」，而是「F 悄悄变成 R」。
